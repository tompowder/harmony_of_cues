Application Logic

This document describes how the game should work internally and how the application should respond to player actions.
Some systems are still being designed. These sections describe the current planned behavior and can be changed during development and balancing.


1. Display and Font

The game uses an ASCII-based interface.
The font used by the game must have equal spacing between every character.
Each character should occupy the same amount of horizontal space.
This is important because the maps use ASCII characters and need to stay aligned.
The font should behave similarly to a monospace font, such as the font used by a basic text editor.

After loading the player's location, the game renders the map on the screen.

The game loads:

Map data
Points of interest
Player location
Available encounters
Required hero data

The ASCII map is rendered using the map.map_data field.
Points of interest are loaded separately using the point tables.
The player is rendered as X.


4. Player Movement

The player moves using the arrow keys.
The player can also press Enter to remain on the current tile without moving.

When the player moves:

Check whether the destination tile can be entered.
If it cannot be entered, do not move the player.
If it can be entered, update the player's X and Y coordinates.
Render the player at the new location.
Check whether the player has entered or interacted with a special point.

The player's position is stored in the player table.

The player can stand on encounter points (.).
The player cannot stand on other special points.
Entering a special point activates it without moving the player onto its tile.

5. Walkable Tiles

The game must detect what the player is attempting to walk into.
Walls cannot be entered.

For example:

| = wall
- = wall

If the player attempts to move into a wall, the movement is cancelled.
The player remains on their current tile.

The same system can later be extended for other blocked or special map tiles.

6. Save Points

Save Points are represented by: S

Save Points are blocked map points. The player does not move onto the S tile.
When the player attempts to move onto a Save Point, the Save Point menu is opened instead.

----------------------
| hp and mp restored |
|                    |
|*Save and continue  |
| Save and quit      |
|                    |
| Exit               |
----------------------

The * shows which option is currently selected.
The player can move the selection using the arrow keys and press Enter to select an option.

When a Save Point is activated The hp and mp of all heroes in the current party is restored to maximum.

If the player selects Save and Continue:
Update the player's current location in the database.
Update the player's saved hero data in the database.
Update the player's equipment ownership and Inventory in the database.
Update which equipment is currently equipped by each hero.
Return the player to the map.
Continue playing from the Save Point.

The saved player data should contain enough information to continue the game from the current location.

If the player selects Save and Quit:
Update the player's current location in the database.
Update the player's saved hero data in the database.
Update the player's equipment ownership and Inventory in the database.
Update which equipment is currently equipped by each hero.
Save all other required player progress.
Return the player to the login page.

Exit
The player returns to the map and continues playing.

8. Information point

Information point are represented by: I

When the player attempts to move onto an Information Point, the Information Point is activated.

When the player activates an Information Point:

The game loads the associated Wild Information.
The information is displayed to the player.
The information is marked as discovered in the player's session.
The discovered information is saved permanently at the next Save Point.

If the information has already been discovered, it can be displayed again without being recorded as new information.

Information Points provide Wild Information.

Wild Information is:
Free
Short
Cryptic
Intended to give the player useful hints
Available before the player has defeated the relevant monster
Not intended to reveal complete statistics or mechanics

example:

------------------------------------
| There is a rare chance to find a |
| Golden Goblin in these woods.    |
| It will flee after some time,    |
| but if you defeat it in time,    |
| you will be richly rewarded.     |

Wild Information is therefore intended to give the player clues, not complete answers.

13. Selecting a Random Encounter

When an encounter is triggered:
Generate a random number between 1 and 100.
Load the encounters available for the current map.
Use their encounter_chance values to determine which encounter is selected.
If the random number does not fall inside an encounter's chance range, no encounter occurs.

Example encounter table:

Red Slime                      30%
Goblin + Red Slime             30%
Forest Wolf                    20%
Forest Wolf x2                 10%
No encounter                   10%

The total chance should equal 100%.

For example:

1–30   -> Red Slime
31–60  -> Goblin + Red Slime
61–80  -> Forest Wolf
81–90  -> Forest Wolf x2
91–100 -> No encounter

If the generated number is 26, the player encounters a Red Slime.
If the generated number is 88, the player encounters two Forest Wolves.
If the generated number is 93, no encounter occurs.

If the selected encounter is No Encounter, no combat is started. 
The player remains on the map and can continue exploring.

15. Calculating Entity Stats

Heroes and monsters use their Level Schema to calculate their base stats.
The Level Schema contains the entity's Level 100 stats.

Example:

max_hp = 800
entity.level = 25

The base HP can currently be calculated as:
800 / 100 × 25 = 200 HP

The final stat is then calculated using other bonuses:

Final Stat =
Base Level Stat
+ Stat Point Bonuses
+ Equipment Bonuses
+ Ability Bonuses

Combat is turn-based.
During a turn, the player selects an action for each hero.
Heroes are selected from left to right.

For example:

Hero 1 → Hero 2 → Hero 3 → Hero 4

Attack, Magic, Run, Skip are actions 
Each hero can select a action:

Attack
Magic
Run
Skip

20. Moves

Moves can:

Deal damage
Heal
Reduce damage taken
Interact with affinities
Participate in synergies

There are three move types:
Attack
Magic
Piercing

Heroes and normal monsters can have a maximum of 4 moves.
the four-move limit is shared between Attack and Magic moves

Bosses can have more than 4 moves.

21. Attack Moves

Attack moves use the attacking entity's Attack stat.

Example:

Tackle

Attack = 10
Power = 1.5

10 × 1.5 = 15 base damage

Attack moves can have an HP cost.

For example:

Tackle
Power: 1.5
Cost: 1 HP

If an attack requires more HP than the entity can spend, the move cannot be used.

22. Magic Moves

Magic moves use the attacking entity's Magic stat.
Magic moves have an MP cost.

For example:

Water Blast
Power: 2.1
Cost: 10 MP

Magic moves have special MP behavior.
If the entity has less MP than the move costs, the move can still be used.

Example:

Current MP: 8
Move cost: 10

Move can be used.

New MP: 0

A magic move cannot be used when the entity has 0 MP.


23. Move Power

Every damaging move has a Power value.
The basic damage calculation starts with:

Attack or Magic × Move Power

Example:

Attack = 10
Power = 1.5

10 × 1.5 = 15

The final damage is then affected by:

Defense
Affinity
Move type
Abilities
Other effects


24. Move Effects

Moves can have additional effects.
The move.effect field stores these effects.

Example:

{
   "effect": "healing"
}

This allows moves to perform actions other than simply dealing damage.
The complete list of possible effects is not finalized yet.


25. Move Affinity

A move can have an Affinity.
The move's Affinity interacts with the target's Affinity.
The relationship is stored in affinity_relationships.

Example:

Water -> Fire = 1.50
Fire  -> Water = 0.75

This means:

Water move against Fire target
= 150% damage

and:

Fire move against Water target
= 75% damage

These values are not final and can be changed during balancing.


26. Move Targets

Moves can have different targeting rules.

The target type is stored in:
move.target

self: Targets the entity that used the move.

ally: Targets one entity on the same side as the move user.

enemy: Targets one enemy.

An enemy is an entity on the opposing side of the encounter.

allies: Targets all allies except the entity using the move.

self_or_ally: Targets either the entity using the move or one ally.

self_and_allies: Targets the entity using the move and its allies.

self_or_ally_or_enemy: Can target any single entity in the encounter.

enemies: Targets every enemy in the encounter.

all_except_self: Targets every other entity in the encounter.
This includes both allies and enemies.

all: Targets every entity in the encounter, including the entity using the move.


27. Move Slots

heroes and monsters can have a maximum of 4 moves.

Example:

1. Tackle
2. Slashing
3. Water Blast
4. Heal

Bosses can have more than 4 moves.

Moves can come from:

Leveling
Shops
Weapons

Weapon moves are temporary.
Weapon moves count towards the four-move limit.
A weapon move cannot be removed through normal permanent move replacement.
If equipping a weapon would exceed the move limit, the player must replace a permanent move.
If the weapon is removed, the weapon-provided move is removed.
The permanent move previously replaced does not return.


28. Move Synergies

After all entities have selected their moves for the turn, the game checks whether the selected moves create a synergy.
The game searches the synergy data for matching move combinations.
If a matching synergy is found, the game checks the participants.
synergy_moves.participant determines which entities are allowed to perform each required move.

Possible participants are:

self
ally
enemy
ally_or_enemy

If all required participants and moves are correct, the synergy activates.
The original moves are replaced by the synergy move.

Example:

Hero 1 -> Water Blast
Hero 2 -> Heal

= SYNERGY Holy Water

Water Blast and Heal are not performed separately.

29. Synergy Calculation

The synergy.calculation field stores the special rules used to calculate the synergy.
By default, a synergy can use the average stats of the participating entities.

Example:

Hero 1 Magic = 20
Hero 2 Magic = 10

Average Magic = 15

The synergy then uses 15 Magic.
A synergy can use a different calculation when required.

Possible calculations include:

Average
Highest
Lowest
Added stats
Target stats
Custom calculations

The exact JSON structure is still being designed.

34. Monster AI

Monster AI determines how monsters behave during combat.
The AI configuration is stored in: model_monster.ai

All monsters use the same AI structure. Different AI features can be enabled 
depending on how complex the monster's behaviour needs to be.

The AI structure contains:
Move Selection
Strategies
Phases
Reactions

Not every monster needs to use all these features.
34.1 Move Selection

Move Selection determines how a monster chooses which move to use during its turn.
The move selection behaviour is configured in model_monster.ai.

Example: json
{
   "move_selection": "random"
}

Each move has a category property that determines what kind of move it is. 
This category is used by the monster AI when selecting moves.

Move Categories:
Offense: Attacking and damage-dealing moves.
Defensive: Defensive, healing and damage-negating moves.
Balanced: General-purpose moves suitable for different situations.
Support: Moves that support allies or provide beneficial effects.

Move Selection Behaviours:
Random: Randomly selects an available move, without considering its category.
Careful: Prefers defensive, balanced and support moves.
Reckless: Prefers offense and balanced moves.
Supportive: Prefers support, defensive and balanced moves.

The AI prefers moves that match its move selection behaviour but 
can still select other available moves when appropriate.
Not every monster needs to use the same move selection behaviour.

More complex AI can use:
Move-selection behaviors
Conditions
Phases
Reactions to combat events

34.2 Strategies

Strategies allow monsters to make more intelligent decisions based on combat conditions.

A strategy can influence:
Which move the monster selects.
Which target the monster selects.
The priority of certain moves or targets.
Which combat situations the monster responds to when making decisions.
Strategy can communicate with another monsters strategy to coordinate a synergie together.


Strategies are evaluated when the monster selects its action.
Example:

A monster can prioritize attacking heroes with low HP.
json

{
   "strategies": 
   [
      {
         "name": "target_weakest",
         "conditions": 
         [
            {
               "stat": "hp_percent",
               "operator": "<=",
               "value": 30,
               "target": "enemy"
            }
         ],
         "priority": 10,
         "target": "lowest_hp_enemy"
      }
   ]
}

In this example:
The monster checks whether an enemy has 30% HP or less.
If the condition is satisfied, the strategy becomes available.
The monster prioritizes targeting the enemy with the lowest HP.

Strategies can also influence move selection.
For example, a monster could prioritize healing when its HP is low or use magic against enemies with high Defense.
If multiple strategies are active, their priorities determine which strategies are preferred.
Strategies do not directly execute moves. They influence the monster's normal move and target selection.

34.3 Monster AI Structure

A monster does not need to use every AI feature.
A simple monster could use: json
{
   "move_selection": "random"
}

A more intelligent monster could use: json
{
   "move_selection": "careful",
   "strategies": 
   [
      {
         "name": "target_weakest",
         "priority": 10,
         "target": "lowest_hp_enemy"
      }
   ]
}

Bosses can use the same strategies, in addition to their phases and reactions.

35. Boss AI

Boss AI extends the normal Monster AI system with additional behaviour.

Bosses can use:
Move Selection
Strategies
Phases
Reactions

This allows bosses to change their behaviour throughout 
combat and respond to actions performed by the player.

35.1 Boss Phases

Bosses can have multiple phases.

Each phase defines the conditions required for the phase to become active.

A phase can define:
A name.
Conditions that determine when the phase is active.
Available moves.
Move-selection behaviour.

All conditions defined for a phase must be satisfied for that phase to become active.

Example: json

{ 
   "phases":

35.2 Strategies

Bosses can also use strategies.
Strategies influence the boss's normal move and target selection.
Strategies work the same way for bosses as they do for normal monsters.
The active phase can also influence which moves are available to the strategies.

35.3 Boss Reactions

Reactions allow bosses to respond to actions and events that occur during combat.
Unlike strategies, reactions can execute an action immediately in response to a specific event.
Reactions are separate from normal move selection and phase behaviour.

35.6 Shared Effect System

Boss AI reactions use the same effect structure as Abilities and Moves.
This allows the game to use a shared Effect Reader to process effects from different systems.

For example, a reaction can:
Execute a move.
Apply a status effect.
Change a stat.
Reduce incoming damage.
Perform other supported effects.

The Effect Reader does not need to know whether an effect originated from a boss reaction, an ability or a move.
It only needs to read the effect data and execute the appropriate operation.
The exact AI JSON structure and available behaviours are still being designed and can be expanded during development and balancing.

37. Taking Damage

The basic damage calculation uses:

Attacking entity's Attack or Magic
Move Power
Affinity multiplier
Target Defense

The current formula is:

((Attack or Magic) x Move Power x Affinity Multiplier) - Effective Defense

for magic moves.
Magic moves can partially ignore Defense.

For example:

Physical move:
Effective Defense = Defense

Magic move:
Effective Defense = Defense × 0.5

39. XP Rewards

The heroes receive XP based on the monsters defeated.

The total XP comes from the monsters' XP rewards.

The current planned party modifiers are:

1 hero -> 100% each
2 heroes -> 75% each
3 heroes -> 66% each
4 heroes -> 50% each

These values are not final.
Each hero receives the specified percentage of the monster's total XP reward. 
The percentage is applied individually to every participating hero and is not divided between the heroes.

The purpose is to prevent a large party from always being strictly better than using fewer heroes.
This system may be removed if testing shows that it does not improve the game.

40. Leveling Up

After receiving XP, the game checks whether a hero has enough XP to level up.
The current XP calculation is only a temporary example.

(level_schema.max_xp / 100 × entity.level) < entity.xp

The final XP requirement will increase with each level and will use a more appropriate progression formula.

When a hero levels up:

Increase the hero's level.
Give the hero a Stat Point.
Allow the player to select which stat to increase.
Check whether the hero learns a new move.
Restore the hero's HP and MP to maximum.

If a hero receives enough XP to gain multiple levels, 
the game repeats the leveling process until the hero 
no longer has enough XP to reach the next level.

44. Application Structure

The application is divided into a frontend, controllers, and services.
The frontend displays the game and sends player input to the backend. 
The backend processes the input using the appropriate service and returns the updated game state to the frontend.

44.1 Website Navigation

When a user visits the website, they are presented with the Login page.
The user can either:

Log in using an existing account.
Navigate to the Register page to create a new account.

After successfully logging in or registering, the user is redirected to the Game page.
The Game page is where the player interacts with the game.

44.2 Game Input

The frontend handles player input, such as:

Arrow keys for movement and menu navigation.
Enter for confirming actions.
Other inputs required by the game.

When the player performs an action, JavaScript sends a request to the Laravel backend without refreshing the entire page.
The request is sent to the GameController.
The GameController:

Receives the player's input.
Validates the incoming data to ensure it has the correct format and contains the required information.
Retrieves the current gameState from the session.
Determines which service should handle the input.
Sends the input to the appropriate service.
Receives the result from that service.
Returns the updated game data to the frontend.

If the input is invalid, the request is rejected 

44.3 Game States

The current game state is stored in the session.
There are three main game states:

map – The player is exploring a map.
encounter – The player is participating in a encounter.
menu – The player is interacting with a menu.

The GameController uses the current game state to determine which service should process the player's input.
For example:

If gameState is map, input is sent to MapService.
If gameState is encounter, input is sent to EncounterService.
If gameState is menu, input is sent to MenuService.

Services can request actions from other services when necessary.
When an action changes the current game state, the session is updated accordingly.

44.4 Services

The application currently uses the following services:

MapService

Handles everything related to map exploration.
Responsibilities include:

Processing player movement.
Checking whether tiles can be entered.
Updating the player's map position.
Detecting points of interest.
Loading and displaying map data.
Requesting encounters when the player activates an encounter point.
Opening menus when the player activates special points.

EncounterService

Handles everything related to combat.
Responsibilities include:

Starting encounters.
Loading heroes and monsters.
Processing combat actions.
Calculating damage and effects.
Checking and activating synergies.
Processing monster AI.
Determining encounter victories and defeats.
Calculating XP, Gold, and equipment rewards.

MenuService

Handles menus and player interactions outside normal map exploration and combat.
Responsibilities include:

Displaying menus.
Processing menu navigation.
Handling Save Point menus.
Handling Shop menus.
Handling equipment purchases.
Handling move purchases and replacements.
Displaying information.
Handling recruitment menus.
Displaying encounter rewards.

SaveService

Handles saving player progress to the database.
Responsibilities include:

Saving the player's current map and coordinates.
Saving hero data.
Saving equipment ownership and inventory.
Saving equipped equipment.
Saving other required player progress.

44.5 Communication Between Services

Services can request actions from other services when an action requires functionality that belongs to another part of the game.
For example, when a player activates an encounter point, MapService requests EncounterService to start an encounter.
Similarly, MenuService can request SaveService to save the player's progress.
Services can also request another service to prepare the next game screen when an interaction is completed.

The following examples describe how the services communicate.
Example 1: Starting an Encounter

When the player moves onto an encounter point (.):

MapService detects that the player has activated an encounter point.
MapService requests EncounterService to start an encounter.
EncounterService selects a random encounter and loads the required monsters.
EncounterService changes the gameState to encounter.
The encounter data is returned to the frontend.
The frontend displays the combat screen.

When the encounter ends:

EncounterService calculates and processes the rewards.
EncounterService changes the gameState to menu if a reward menu needs to be displayed.
EncounterService requests MenuService to display the encounter rewards.
The player interacts with the reward menu.
When the menu is closed, MenuService requests MapService to return to the map.
MapService prepares the map data.
The gameState is changed to map.
The frontend displays the map.

Example 2: Activating a Save Point
When the player attempts to move onto a Save Point (S):

MapService detects the Save Point.
The player does not move onto the Save Point tile.
MapService requests MenuService to display the Save Point menu.
MenuService changes the gameState to menu.
The frontend displays the Save Point menu.

If the player selects Save and Continue:

MenuService requests SaveService to save the player's progress.
SaveService updates the required player data in the database.
MenuService requests MapService to return to the map.
MapService prepares the map data.
The gameState is changed to map.
The frontend displays the map.

If the player selects Save and Quit:

MenuService requests SaveService to save the player's progress.
SaveService updates the required player data in the database.
The player is logged out.
The player is redirected to the Login page.

If the player selects Exit:

The Save Point menu is closed.
MenuService requests MapService to return to the map.
The gameState is changed to map.
The frontend displays the map without saving.
